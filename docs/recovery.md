# Recovery

This stack has three recovery surfaces, ordered by ease of use:

1. **Updater Console** at `http://localhost:3003` — Versions tab has "Switch to previous version" / "Roll back"; Dashboard has per-service Start / Stop / Restart and a self-update affordance.
2. **Doctor Console** at `http://localhost:3004` — read-only probes (Health, Drift) + Snapshots browser + a Recover tab that restores Quadlets from the last-known-good snapshot.
3. **`~/.local/bin/signalk-recovery`** — pure-bash SSH safety net. Works with zero containers running.

Try the highest-numbered one you can still reach. Each surface is independent: the doctor doesn't depend on the updater, and `signalk-recovery` doesn't depend on either container.

## Anatomy: where state lives

| Path | What's in it | Backed up by |
|---|---|---|
| `~/.signalk/` | SignalK config, plugins, security | signalk-backup (separate plugin) |
| `~/.signalk-updater/token` | Bearer auth token for the updater (mode 0600) | not backed up; regenerated by reinstall |
| `~/.signalk-updater/hardware.json` | Hardware passthrough config | reproducible from `detect-hardware.sh` |
| `~/.signalk-updater/operation.lock` | Cross-engine mutex. Held during version switches, self-updates, doctor-switches, hardware-applies, recovery. Should release in seconds to minutes (no flow is intended to hold it longer than the health-poll timeout of 180s + a small rollback budget). See ["stuck operation.lock"](#stuck-operation-lock) below for what to do if it lingers. | transient |
| `~/.signalk-doctor/token` | Bearer auth token for the doctor (mode 0600) | not backed up |
| `~/.signalk-doctor/signalk-token` | Admin signalk-token (mode 0600) used by the doctor's drift scanner to query `/skServer/diagnostics`. Generated by the installer via `signalk-generate-token`. Rotation is operator-initiated. | not backed up; regenerable via `podman exec signalk-server signalk-generate-token -u admin -e 5y` |
| `~/.signalk-doctor/snapshots/` | Every Quadlet write is snapshotted here (last 10 per file; `last-good` snapshots are never pruned) | this is the backup |
| `~/.signalk-doctor/last-good.json` | The validated last-known-good tag set + snapshot paths. Bootstrap-complete marker. | regenerated on each successful switch |
| `~/.config/containers/systemd/signalk-*.container` | Active Quadlets — rewritten by the updater on switch / hardware-apply. The updater rewriter only touches the `Image=` line; the rest of the Quadlet (env vars, `StopTimeout`, mounts, etc.) is preserved verbatim. | mirror in snapshots/ |
| `~/.local/bin/signalk-recovery` | Host-resident bash recovery | installed by the bash installer; refreshable via `signalk update` |

## Scenario: signalk-server is broken but the engines are fine

1. Open Updater Console → "Logs" → look for the error.
2. If a recent version switch went wrong, click "Roll back to previous version".
3. If that fails, open Doctor Console and click "Recover" — this restores Quadlets from the last validated snapshot.

## Scenario: the updater itself is broken (bad self-update, crashloop)

1. Open Doctor Console at `http://localhost:3004`.
2. Click "Recover" — this also restores the updater's Quadlet to the last-known-good snapshot.
3. Wait for the updater container to restart on the old image. systemd's auto-restart-after-failure timer can take up to ~90s before the new container actually starts (this is a known systemd-user behavior, not a bug); the updater's own version-switch flows use explicit `StopUnit` + `StartUnit` to bypass it but the doctor's recovery path goes through systemd's normal restart.

If `Restart=on-failure` + `StartLimit*` (5 starts in 5 minutes) trips, the unit goes to `failed` state. Reset it from SSH:

```bash
systemctl --user reset-failed signalk-updater-server.service
systemctl --user start signalk-updater-server.service
```

## Scenario: both engines are down (the worst case)

Open SSH and use the bash recovery script:

```bash
~/.local/bin/signalk-recovery status         # what's running, what's broken
~/.local/bin/signalk-recovery doctor         # full diagnostics dump
~/.local/bin/signalk-recovery rollback-all   # restore every Quadlet from last-known-good
```

`rollback-all` will:

1. Copy the newest `~/.signalk-doctor/snapshots/*-<unit>.container` over each active Quadlet.
2. `systemctl --user daemon-reload`.
3. `systemctl --user try-restart` each affected service.

No containers need to be running for this to work — it's pure bash + systemd.

## Scenario: stuck operation.lock

`~/.signalk-updater/operation.lock` is a cross-engine file mutex serialising version switches, self-updates, doctor-switches, hardware-applies, and recovery operations. Every flow acquires it in a `try`/`finally` so it normally releases in seconds (a clean stop) to a few minutes (a switch that times out and rolls back).

If you see `Self-update failed: operation lock held by updater/<operation> since <timestamp>` more than ~5 minutes after the operation started, the lock is likely stale (the prior operation either crashed or got stuck in a code path that doesn't release on its `finally`).

To check:

```bash
cat ~/.signalk-updater/operation.lock      # shows owner/operation/startedAt
```

To clear:

```bash
rm ~/.signalk-updater/operation.lock
```

The lock lives on a host bind-mount (`~/.signalk-updater/`), so restarting the updater container doesn't clear it on its own — only `rm` (or a re-run of the previously-stuck operation reaching its own `finally`) does. After removing the file, retry the operation that was blocked.

## Scenario: lost admin password (locked out of the Admin UI)

```bash
signalk resetadmin            # resets (or creates) the user "admin"
signalk resetadmin alice      # same, for a different username
```

Prompts for a new password, upserts the user's bcrypt hash in `~/.signalk/security.json` (hashing happens inside the signalk-server container with the server's own bcryptjs), and restarts signalk-server. The JWT `secretKey` is preserved, so existing API tokens — including the doctor's drift-scanner token at `~/.signalk-doctor/signalk-token` — stay valid.

This is preferable to the [upstream documented recovery](https://demo.signalk.org/documentation/Security.html#disabling-security-lost-admin-credentials) (delete `security.json`, restart, re-create the admin from the "Enable Security" screen), which works in this stack too but throws away the `secretKey` and with it every issued token; after that recovery the installer must be re-run to mint a fresh doctor token. Note that deleting `security.json` does **not** disable security — the strategy lives in `settings.json` — it only resets the user list, and the change takes effect after a server restart (`systemctl --user restart signalk-server`), not on a browser reload.

## Scenario: corrupted state files

The `~/.signalk-doctor/snapshots/` directory is the source of truth for recovery. If the snapshots themselves are gone:

- Re-run the bash installer (`curl -fsSL ... | bash`). It is idempotent and will re-pull images and re-write fresh Quadlets, marking the new state as "bootstrap-complete" in `last-good.json`.
- This preserves `~/.signalk/` (your SignalK config + plugins) and `~/.signalk-backup/` (your backup repo if present).

## Journald retention

The installer drops `/etc/systemd/journald.conf.d/signalk.conf` with `SystemMaxUse=500M` and `MaxRetentionSec=14day`. On a Pi this prevents the SD card from filling.

If you skipped that step (sudo unavailable at install time), apply it later:

```bash
sudo tee /etc/systemd/journald.conf.d/signalk.conf >/dev/null <<EOF
[Journal]
SystemMaxUse=500M
MaxRetentionSec=14day
EOF
sudo systemctl restart systemd-journald
```

## When even SSH is gone

If you can't even SSH:

- For a boat: physical access. A USB stick with the install.sh + the bash recovery script copied to `~/.local/bin/signalk-recovery` will get you back into the stack from a freshly-installed Linux session.
- The fallback is always `curl -fsSL https://dirkwa.github.io/signalk-universal-installer/installer/linux/install.sh | bash` — the installer is idempotent and will heal a half-broken state.

## What is NOT recoverable from these mechanisms

- **A wiped `~/.signalk/`** — only [signalk-backup](https://github.com/dirkwa/signalk-backup) can restore that. The recovery surfaces here are for the **container stack** that runs around signalk-server, not signalk-server's data.
- **Lost auth tokens.** If you delete `~/.signalk-updater/token`, the Updater Console becomes inaccessible (UI gets 401s on every mutating call). Re-run the installer to regenerate.
